CRITICAL: revalidateTag(tag, "max") is the correct function from BOTH route handlers AND server actions.
updateTag() does NOT work from route handlers. Since routes call these facade methods, and
'use server' actions can themselves be called from routes (the calling route doesn't need 'use server'),
we use revalidateTag(DASHBOARD_CACHE_TAG, "max") throughout — per RESEARCH Critical Finding #1.

The 5 mutation methods and their signatures (per D-28 + 03-PATTERNS.md §actions.ts):

1. setStudentAction(input: { studentKey: string; studentName: string; parentName: string; status: StudentActionStatus; updatedByEmail: string; updatedByName: string }): Promise<void>
   - Postgres write: upsertFollowUpState(input) + appendFollowUpLog({ ...input, actionType: "set" })
   - Cache: revalidateTag(DASHBOARD_CACHE_TAG, "max") + recordCacheInvalidation(...)

2. clearStudentAction(input: { studentKey: string; studentName: string; parentName: string; actorEmail: string; actorName: string }): Promise<void>
   - Postgres write: appendFollowUpLog({ ...input, actionType: "clear", status: null })
   - Cache: revalidateTag(DASHBOARD_CACHE_TAG, "max") + recordCacheInvalidation(...)

3. bulkSetAction(input: { updates: Array<{ studentKey: string; studentName: string; parentName: string; status: StudentActionStatus }>; actorEmail: string; actorName: string }): Promise<void>
   - Postgres write: dbBulkSetStudentAction(input) — single transaction per D-25
   - Cache: revalidateTag(DASHBOARD_CACHE_TAG, "max") + recordCacheInvalidation(...)

4. markInactiveStudent(input: { studentKey: string; studentName: string; parentName: string; markedByEmail: string; markedByName: string }): Promise<void>
   - Postgres write: dbMarkInactive(input)
   - Cache: revalidateTag(DASHBOARD_CACHE_TAG, "max") + recordCacheInvalidation(...)

5. clearInactiveStudent(studentKey: string): Promise<void>
   - Postgres write: dbClearInactive(studentKey)
   - Cache: revalidateTag(DASHBOARD_CACHE_TAG, "max") + recordCacheInvalidation(...)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| route handler → actions.ts | Route handlers call mutation facade methods with session-user actor attribution |
| actions.ts → Postgres | All writes include actor fields (email, name) enforced at type level via FollowUpStateInsert.notNull() |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04-1 | Tampering | race condition in write→revalidateTag ordering | mitigate | D-28: Postgres write is awaited BEFORE revalidateTag. revalidateTag is synchronous (no await needed). If write throws, revalidateTag never executes. If write succeeds but process dies before revalidateTag — cache serves stale data until TTL expiry (60s). Accept: no data loss; minor freshness gap |
| T-03-04-2 | Spoofing | actor attribution bypass | mitigate | Mutation method signatures require updatedByEmail + updatedByName as non-optional fields. Callers (route handlers) get these from requireSessionUser() which validates the NextAuth session. Type enforcement via FollowUpStateInsert.notNull() at DB level |
| T-03-04-3 | Elevation of Privilege | 'use server' Server Action exposes mutations as POST endpoints | mitigate | Server Actions invoked via fetch POST have implicit CSRF protection in Next.js 16 (same-origin + content-type check). Actions are also only invoked from protected route handlers that call requireSessionUser() first |
</threat_model>
