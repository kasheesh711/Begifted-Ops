### Rollback strategy (D-27)

- **D-27:** **Vercel dashboard rollback** is the first-line rollback mechanism. If the cutover PR regresses production, an operator clicks Promote Deployment on the prior build in the Vercel dashboard — swap completes in <30s, pre-cutover build takes traffic again.
- **Secondary cleanup:** `git revert <cutover-merge-SHA>` + push, restoring main branch to the pre-cutover state. Forward fix then cherry-picks the good parts.
- **Why not feature flags:** ROADMAP explicitly rejects feature flags ("No feature flags — module-swap PRs are the cutover mechanic"). Rollback is build-level, not code-path-level.
- **Rollback readiness requirement:** Phase 3 must leave the pre-cutover Vercel build (the "last known good" pre-merge deploy) reachable via Vercel's deployment history. Default Vercel behavior preserves this; no special config needed.
- **Ripple:** PR description includes a "Rollback plan" section stating "If dashboard errors >5% on /api/dashboard or /api/actions within 30 minutes of promotion to production, operator promotes previous deployment from Vercel dashboard. Ping Kevin. Root-cause analysis before forward fix."

### Cache lifetime + invalidation surface (D-28)

- **D-28:** `cacheLife({ expire: 60 })` mirrors current `unstable_cache { revalidate: 60 }` TTL. Wraps the full dashboard payload build in service.ts.
- **Mutation surface (5 sites MUST call `updateTag('dashboard-payload')` after their Postgres commit):**
  1. `setStudentAction(studentKey, status, actor)` — single-student action
  2. `clearStudentAction(studentKey, actor)` — single-student clear
  3. `bulkSetStudentAction(studentKeys[], status, actor)` — bulk action (routes through `bulkDb` per D-25)
  4. `markInactive(studentKey, actor)` — inactive-student add
  5. `clearInactive(studentKey, actor)` — inactive-student remove
- **Pattern:** Each mutation's implementation = Postgres write FIRST, then `updateTag` SECOND. `updateTag` never runs if the write throws. Inverted order would cache-invalidate with no DB change (wasted work) or, worse, cache-miss before the new value is readable (short window where dashboard shows the pre-write value after an apparent success).
- **`DASHBOARD_CACHE_TAG` constant** stays in `web/src/lib/dashboard/config.ts` — value `"dashboard-payload"`. Don't rename.
- **Zero additional tags at this phase.** Per-student tags (`student-<key>`) are a v2 OPS optimization; Phase 3 uses one tag for simplicity.

### SVC-07 /api/health JSON shape (D-32)

- **D-32:** Structured per-subsystem status:
  ```ts
  // GET /api/health response
  {
    status: "ok" | "degraded" | "down",
    timestamp: string,          // ISO 8601
    subsystems: {
      wisenet: {
        status: "ok" | "degraded" | "down",
        latencyMs?: number,
        error?: string
      },
      postgres: {
        status: "ok" | "degraded" | "down",
        latencyMs?: number,
        error?: string
      },
      auth: {
        status: "ok" | "down",   // Presence of env vars; no live probe
        error?: string
      }
    },
    deployedAt?: string,          // populated if process.env.VERCEL_DEPLOYMENT_ID is set
    // deploymentId deliberately omitted — Phase 4 DEPL-06 formalizes via X-BG-Deploy-Id header
  }
  ```
- **Wisenet probe:** HEAD or cheap `GET /institutes/v3/{centerId}/students?page_size=1` through the retry wrapper with 1 retry cap (shorter than client default — health endpoint must fail fast).
- **Postgres probe:** `SELECT 1` via the HTTP driver (`db.execute(sql\`SELECT 1\`)`). No Pool usage — HTTP is fine.
- **Auth probe:** `getAuthEnv()` succeeds → `"ok"`; throw → `"down"` with error (no live NextAuth token mint).
- **Status rollup rule:**
  - Any subsystem `"down"` → overall `"down"`
  - Any subsystem `"degraded"` (not down) + no downs → overall `"degraded"`
  - Everything `"ok"` → overall `"ok"`
- **Response status code:** `200` for `"ok"` and `"degraded"`; `503` for `"down"` (catches uptime monitors).
- **Caching:** Health endpoint does NOT use `'use cache: remote'` — must probe live on every call.

  ```ts
  // web/src/lib/runtime/logger.ts
  type LogLevel = "error" | "warn" | "info";
  export function log(level: LogLevel, route: string, error: unknown, extra?: Record<string, unknown>) {
    const payload = {
      ts: new Date().toISOString(),
      level,
      route,
      error: error instanceof Error ? { name: error.name, message: error.message, stack: error.stack } : String(error),
      ...extra,
    };
    // console.error even for warn/info — Vercel captures all console.* at function level
    console.error(JSON.stringify(payload));
  }
  ```
